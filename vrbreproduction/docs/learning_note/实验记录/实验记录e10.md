# e10 2026-5-20

## 一、E10 实验设计思路

E10 不是从头再发明一套新算法，而是专门回答 E9 留下的一个关键问题：

> E9 的结构改动到底已经足够好，只是没真正跑上 CoTracker；还是说 E9 的提升本身就主要来自 fallback LK，换成真实 CoTracker 也不会更好？

因此，E10 的核心目标非常明确：

1. 保留 E9 已经验证有效的语义设计；
2. 不回到 background homography，也不靠放宽 threshold 刷覆盖率；
3. 把真实 CoTracker 接到 E9 的 contact-part 跟踪主路径上；
4. 用完整 100 subaction 正式实验，验证真实 CoTracker 相对 E8 / E9 是否继续带来增益。

换句话说，E10 主要想总结和解决的是下面两个问题。

### 1. E9 的“算法结构”和“跟踪器后端”被混在了一起

E9 最终达到：

- 覆盖 `74/100`
- final tuple `147`

但它其实没有真正跑上 CoTracker，而是：

- `cotracker_init_status = failed`
- `cotracker_init_error = ModuleNotFoundError: No module named 'torch'`
- `tracker_backend = fallback_lk`

这意味着 E9 的提升虽然真实存在，但它回答的只是：

> contact-part local projection + part-aware gate + continuation_entry_rescue 这套结构有效。

它没有回答：

> 如果把跟踪器从 fallback LK 换成真实 CoTracker，这套结构会不会更稳、更准、覆盖更高？

### 2. 现有瓶颈里，哪些是跟踪问题，哪些不是跟踪问题

E8 和 E9 的主要失败原因里，既有：

- `track_confidence_below_threshold`
- `track_visibility_below_threshold`

这样的跟踪问题，也有：

- `missing_hand_or_object_bbox`
- `contact_points_lt5_after_object_boundary_filter`

这样的检测 / 接触点问题。

E10 的意义就在于把“真实 CoTracker”这个变量单独拉出来。这样就能更清楚地区分：

- 跟踪器换强以后，哪些失败真的减少了；
- 哪些失败与 CoTracker 无关，仍然卡在 detection / contact point / gate 之前。

## 二、E10 用了什么办法

E10 采用的是：

> E9 语义结构 + 真实 CoTracker 后端

它保留了 E9 的三项核心改动，同时把 CoTracker 真正接入 contact-part points 的主路径。

### 1. 保留 E9 的 contact-part 局部建模

E10 没有推翻 E9 的局部部件思路，而是继续使用：

- `contact_part_mask`
- contact-part 优先的 tracking point sampling
- `contact_part_local_affine`
- `part-aware gate`

这意味着 E10 仍然坚持：

- heatmap 表示 reference frame 上未来手会接触物体的位置；
- 最终 contact point 仍来自 hand-object contact 区域拟合得到的 5 个 GMM center；
- trajectory 仍然是 post-contact active hand / wrist trajectory，而不是物体轨迹。

### 2. 保留 E9 的 candidate 语义约束

E10 继续优先使用：

- `new_contact_episode`

只有在一个 subaction 内完全没有 new contact episode 候选时，才允许：

- `continuation_entry_rescue`

也就是说，E10 没有把“所有 continuation contact 都放进来”，而是沿用 E9 那种非常保守的边界补救策略。

### 3. 真正启用 CoTracker 做 contact-part points 跟踪

E10 的关键变化，不是 gate 重写，而是把跟踪主路径从：

- `fallback_lk`

换成了：

- `cotracker`

并且要求 diagnostics 里明确区分：

- `tracker_backend`
- `cotracker_init_status`
- `cotracker_init_error`

最终正式实验的结果已经确认：

- `cotracker_init_status = ready`
- `fallback tracker 成功数 = 0`
- `tracker_backend_final = cotracker`

也就是说，这次不是“接口上写了 CoTracker，实际上还是 LK”，而是真正跑起来了。

## 三、E10 流程是什么样的

E10 的完整流程可以概括为 8 步。

### 1. 在每个 subaction 内寻找 candidate

仍然只优先从：

- `new_contact_episode`

中取候选；如果一个 subaction 完全没有 new-contact 候选，再启用：

- `continuation_entry_rescue`

### 2. 在 contact frame 上确定当前接触物体

沿用 E8 / E9 的 active object 选择逻辑，从 hand-object detection 中找到当前 hand 对应的 active object。

### 3. 构造 whole-object mask 和 contact_part_mask

先拿到 whole-object mask，再结合：

- contact GMM means
- raw contact points
- hand bbox
- noun-conditioned soft prior

构造局部的 `contact_part_mask`。

### 4. 从 contact_part_mask 优先采样跟踪点

采样策略依然是：

- 优先从 contact part 区域采样；
- 点不够时补 whole-object boundary；
- 尽量避免大量 interior 点支配局部运动估计。

### 5. 用 CoTracker 把这些局部点跟到 reference frame

E10 的真正新变量就在这里：

- 用真实 CoTracker 跟踪 contact-part dominated points；
- 不再把 fallback LK 当成主路径；
- 如果 CoTracker 初始化失败，diagnostics 要明确记出来，而不是悄悄回退并伪装成功。

### 6. 用 tracked local points 拟合局部 affine

在 reference frame 上，根据可见、可信的局部跟踪点拟合：

- `contact_part_local_affine`

再把 5 个 GMM center 从 contact frame 投影到 reference frame。

### 7. 做 part-aware gate

最终不只是检查 projected contact 是否还在“整个物体上”，而是进一步检查：

> projected contact 是否落在 reference contact part 上

只有少数小物体等情况，才允许更宽松的 whole-object fallback。

### 8. 生成 trajectory、heatmap 和最终导出

如果 projected contact、trajectory 和语义约束都通过，就生成：

- projected 5-point contact representation
- post-contact hand trajectory
- label heatmap
- final tuple

最终导出时仍然采用：

- 每个 subaction 最多 `3` 个 tuple
- 同一 subaction 内近邻帧至少间隔 `2` 帧

## 四、E10 与之前实验有什么区别

### 1. 相比 E7：从 object-aware 粗投影走到 contact-local 投影

E7 的主线是：

- detection-assisted sparse optical flow
- object tracklet
- bbox / tracked-object gate

它已经放弃 background homography，但仍然比较粗，更多是在问：

> 物体大概在哪里，接触点有没有还落在这个 tracked object 里面？

E10 则进一步问：

> 接触点是否还落在“正确的接触部件”上？

所以 E10 相比 E7 的区别是：

- 表示更局部；
- gate 更语义化；
- 跟踪后端更强；
- 导出 tuple 数也不再被限制为每个 subaction 只保留 1 个。

### 2. 相比 E8：从 whole-object mask gate 走到 part-aware gate

E8 已经把思路从 bbox 升级到了：

- object mask
- mask 内 object point tracking
- whole-object mask gate

但 E8 的 gate 仍然是 whole-object 级别。只要 projected contact 还落在整个物体 mask 内，就可能放行。

E10 与 E8 的核心区别是：

- E8 关心“还在物体上”
- E10 关心“还在正确接触部件上”

此外，E8 虽然名义上引入 CoTracker，但正式结果其实全是：

- `fallback_lk`

E10 则真正把 CoTracker 跑起来了。

### 3. 相比 E9：结构不变，但后端变量被真正验证

E9 与 E10 的结构几乎一致，差别不在语义流程，而在：

- E9：CoTracker 初始化失败，主路径实际是 fallback LK
- E10：CoTracker 初始化成功，主路径实际是 CoTracker

因此可以把 E10 看成：

> 对 E9 结构的一次“真实后端验证版”

它的价值不是“发明新结构”，而是把 E9 从“结构正确但 CoTracker 没启用”推进到“结构正确且 CoTracker 真正跑完”。

## 五、E10 与之前实验的指标对比

### 1. 总体结果对比

| 实验 | 核心方案 | 覆盖 subaction | final tuple | CoTracker 状态 | tracker backend 结果 |
| --- | --- | ---: | ---: | --- | --- |
| E7 | object tracking + sparse optical flow + tracked-object gate | 43 | 43 | 无 | local flow / bbox relative |
| E8 | whole-object mask point tracking + whole-object mask gate | 60 | 131 | 未真正启用 | `fallback_lk = 100%` |
| E9 | contact-part local projection + part-aware gate + continuation entry rescue | 74 | 147 | 初始化失败 | `fallback_lk = 100%` |
| E10 | E9 结构 + 真实 CoTracker | 79 | 157 | `ready` | `cotracker = 100%` |

### 2. E10 相对 E8 / E9 的增量

相对 E8：

- subaction 覆盖：`60 -> 79`，增加 `19`
- final tuple：`131 -> 157`，增加 `26`

相对 E9：

- subaction 覆盖：`74 -> 79`，增加 `5`
- final tuple：`147 -> 157`，增加 `10`

这说明两件事：

1. E9 的结构性改进本身已经非常重要；
2. 在 E9 结构不变的前提下，真实 CoTracker 仍然继续带来了可观增益。

### 3. Funnel 指标对比

| 指标 | E8 | E9 | E10 |
| --- | ---: | ---: | ---: |
| deep run candidate total | 556 | 624 | 624 |
| object_track_success | 332 | 386 | 409 |
| reference_found | 305 | 346 | 365 |
| projection_success | 305 | 346 | 365 |
| trajectory_success | 305 | 346 | 365 |
| heatmap_success | 131 | 147 | 157 |

这个对比很关键：

- E9 相比 E8，主要说明 part-aware 结构有效；
- E10 相比 E9，在 candidate 总量不变的前提下，`object_track_success / reference_found / projection_success / trajectory_success` 全部继续上升；
- 因此 E10 的新增收益，主要可以归因于真实 CoTracker 提升了跟踪与局部投影的稳定性。

### 4. 失败原因对比

E9 的主要失败原因：

- `track_confidence_below_threshold = 81`
- `missing_hand_or_object_bbox = 79`
- `contact_points_lt5_after_object_boundary_filter = 71`
- `part_gate_failed = 16`

E10 的主要失败原因：

- `missing_hand_or_object_bbox = 79`
- `contact_points_lt5_after_object_boundary_filter = 71`
- `track_confidence_below_threshold = 51`
- `part_gate_failed = 23`

可以看到：

1. `track_confidence_below_threshold` 从 `81` 降到 `51`，这是 E10 最直接的改进证据，说明真实 CoTracker 确实缓解了跟踪不稳定。
2. `missing_hand_or_object_bbox` 完全没变，仍然是 `79`。这说明检测缺失不是 CoTracker 能解决的问题。
3. `contact_points_lt5_after_object_boundary_filter` 也没变，仍然是 `71`。这说明接触点构造不足也不是跟踪器升级能直接解决的问题。
4. `part_gate_failed` 从 `16` 升到 `23`，说明 CoTracker 让更多候选成功走到了后面的 part-aware gate 阶段，因此 gate 反而更真实地暴露出局部语义不一致的问题。

所以 E10 的结论不是“所有问题都解决了”，而是：

> 跟踪端明显变强了，但剩余瓶颈已经更集中在 detection 和 contact point 本身。

## 六、E10 的最终结论

E10 回答了最初的问题：

### 1. E10 到底用了什么办法

它用的是：

- E9 的 contact-part local projection
- E9 的 part-aware gate
- E9 的 continuation_entry_rescue
- 再加上真实 CoTracker 作为跟踪主路径

### 2. 这个流程是什么样的

流程是：

- candidate 选择
- active object 选择
- whole-object mask / contact_part_mask 构造
- contact-part points 采样
- CoTracker 跟踪到 reference frame
- 局部 affine 投影 5 个 GMM centers
- part-aware gate
- 生成 heatmap 和 post-contact hand trajectory

### 3. 它和之前实验最大的区别是什么

最大的区别不是又换了一套 gate，而是：

> E10 把 E9 这套已经证明有效的语义结构，第一次和真实 CoTracker 成功组合起来了。

### 4. 最终效果如何

E10 的正式结果是：

- 覆盖 `79/100` 个 subaction
- 生成 `157` 个 final tuple
- `cotracker_init_status = ready`
- final tuple 的 `tracker_backend = cotracker`
- `fallback tracker 成功数 = 0`

因此，E10 可以被视为当前阶段最完整、最可信的一版：

- 它继承了 E9 的结构正确性；
- 它补上了 E9 缺失的真实 CoTracker 验证；
- 它相对 E9 继续带来了 `+5` subaction、`+10` tuple 的增益；
- 它也更清楚地暴露出剩余瓶颈主要在 detection 和 contact point，而不再主要卡在跟踪器本身。

### 5. 还没解决什么

E10 还没有解决的核心问题是：

- `missing_hand_or_object_bbox`
- `contact_points_lt5_after_object_boundary_filter`
- 部分 `part_gate_failed`

也就是说，后续如果还要继续往上走，重点可能不再是简单换更强跟踪器，而是：

1. 提高 hand / object detection 的稳定性；
2. 提高 contact point 构造质量；
3. 让 reference part mask 的表达更稳，而不只是轻量规则构造。
