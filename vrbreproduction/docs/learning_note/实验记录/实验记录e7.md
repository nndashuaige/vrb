## 十二、E7 GPU 改造（2026-05-18 晚）

### 1. 这次改造的目标

本轮不是把 E7 全流程重写成 GPU pipeline，而是在尽量不改整体流程、不改输入输出目录结构的前提下，让 E7 里最适合 GPU 的热点先走 GPU。

当前 E7 的主要重计算路径里，最值得优先改的是候选循环内重复发生的 sparse optical flow（稀疏点跟踪）：

- `track_object_backward()`
- `track_contact_projection_local_flow()`

这两段原本都依赖 OpenCV CPU 的 `cv2.calcOpticalFlowPyrLK()`。

由于云端当前安装的是 `opencv-python-headless==4.13.0.92`，其 CUDA device count 为 `0`，不能直接走 OpenCV CUDA optical flow。因此本轮采用的最小可行方案是：

- 保留原来的 OpenCV CPU 路径作为 fallback
- 在 E7 主脚本中新增一个可选 PyTorch CUDA patch matching backend
- 当 `torch.cuda.is_available()` 为真时，优先用 GPU 做局部 patch 搜索和 forward-backward check
- 若 GPU 不可用、torch 不存在、或局部点不满足条件，则自动回退原有 OpenCV CPU 逻辑

### 2. 本地代码修改

本轮修改文件：

- `/Users/huhu/Documents/Code/bishe/vrb/vrbreproduction/src/vrbreproduction/e7_object_tracking_projection.py`

主要改动：

1. 在 `E7Config` 中新增 GPU flow 配置项：
   - `gpu_flow_enabled`
   - `gpu_flow_device`
   - `gpu_flow_patch_radius`
   - `gpu_flow_search_radius`

2. 新增 GPU flow backend 相关函数：
   - `get_torch_for_gpu_flow()`
   - `describe_gpu_flow_backend()`
   - `track_points_backward_torch_patch()`

3. 改造 `track_points_backward()`：
   - 先尝试 PyTorch CUDA patch backend
   - 失败时自动回退 OpenCV CPU `calcOpticalFlowPyrLK`

4. 在：
   - `track_object_backward()`
   - `track_contact_projection_local_flow()`

   中把 `config` 传入 `track_points_backward()`

5. 在 `run_e7_experiment()` 启动时打印实际 optical-flow backend，并在结束时打印 runtime stats。

## 六、为什么最后不用 Docker

本轮实际测试过在云端安装 Docker。

结论不是“Docker 命令装不上”，而是：

- `docker.io` 可以安装
- `dockerd` 也可以在某些受限参数下拉起来
- 但 `docker build` / `docker run` 需要的宿主权限在当前 SmoothCloud 实例里不完整
- 实际遇到过：
  - `iptables Permission denied`
  - `unshare: operation not permitted`

同时手册里真正支持的路线是：

- `/root/workspace` 持久化
- “存储镜像”保存实例环境

而不是“实例内部再自建 Docker”

所以 E7 当前正确的工程路径是：

- 数据放 `/root/workspace/vrb`
- 代码放 `/root/workspace/vrb/vrbreproduction`
- 用 `.venv` 裸跑
- 跑通后用平台控制台“存储镜像”保存环境

## 九、平台使用建议

### 1. 重要文件都放 `/root/workspace`

后续凡是需要保留的，都尽量放：

- `/root/workspace/vrb/vrbreproduction`
- `/root/workspace/vrb/logs`

不要把关键改动只放在系统其他临时路径。

### 2. 跑通后尽快在控制台点“存储镜像”

因为 SmoothCloud 官方支持的是这个流程。

推荐在以下时机存镜像：

- E7 依赖环境确认稳定后
- E7 跑通后
- E8 新依赖或大改动跑通后

这样以后新开实例时，可以直接恢复环境，不必重装一遍。

### 3. 代码最好本地和云端双保存

云端方便跑实验，本地方便：

- 版本管理
- 做对比
- 写实验记录
- 防止误删

所以建议：

- 本地是主代码仓
- 云端是运行副本
